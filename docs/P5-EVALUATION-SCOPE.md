## 3. New evidence I can produce honestly (the Simulator tab)

I ran a first experiment to see what is worth showing: the engine's per-component waiting formula against the **exact textbook M/M/c result (Erlang C)**. Preliminary result, to be regenerated by the real generator:

- With one server the two agree exactly.
- With several servers the model's formula is an approximation, and **in relative terms it overestimates the wait a lot when the load is low and there are many servers** (for example 16 servers at 50% busy: about three times the exact wait). At those loads the waits are tiny.
- Where the wait is at least 20% of the service time, the worst relative error is **15.2%**; at least 5%: 43%; at least 1%: 115%.
- The largest gap anywhere in absolute terms is **0.034 of one service time** (about 0.7 ms on the 22 ms app tier).
- Real components in the model have 11 to 480 servers, which is the region where the approximation is least tight at low load and tight near saturation.

So the honest statement is: "close to exact where waiting matters, loose where it does not matter". That is worth saying plainly, with the table behind it, rather than hiding it.

The tab would show four measured things, all computed by the real engine (not typed in):

1. **Exact textbook comparison** (M/M/1 exact; M/M/c against Erlang C over a grid of servers and loads, with relative and absolute error and where the waiting is large enough to matter).
2. **Port fidelity**: the largest difference between the TypeScript engine and the six reference fixtures, and how many values were compared.
3. **Internal consistency checks** across the six templates: the same input always gives the same output; p95 never improves as load rises along the Limits curve; the load just under the breaking point meets the goal and the load just over it does not.
4. **What none of this proves**, in plain words.

## 5. How the data gets there

A generator in the API (`pnpm fixtures:evaluation`, same pattern as Learn and Examples) runs the real engine and the Erlang C maths and writes `web/src/lib/evaluation-data.json`. A backend spec fails if the stored file differs from a fresh run. Every reproduction command shown on the page is a real script, and a test checks each one exists in `package.json`.

## 6. Decisions needed (recommendation first)

1. **What the Simulator tab shows.** Recommended: the four items in section 3. Alternative: only the port-fidelity and M/M/1 items (less informative, nothing awkward to explain).
2. **Public or signed-in.** Recommended: make `/evaluation/*` **public**: it holds no personal data and anyone judging the project needs to see the evidence without an account. This changes two registry entries from app to public; the route count stays 40. Alternative: keep it signed-in.
3. **How to word the Erlang C finding.** Recommended: say plainly that the formula is an approximation, show relative and absolute error and the region where it matters, and note that this checks one part of the model (the per-component wait), not the final p95. Alternative: show only the "close to exact where it matters" half (selective, so I advise against it).
4. **Whether to change the formula.** Recommended: no. Switching to exact Erlang C would change every number and every fixture and break the parity with the original prototype; record it as a possible future improvement instead.
5. **Calibration.** Recommended: method only, no experiment now (as approved). Alternative: run a real stepped load test in this phase (a separate piece of work on this memory-limited laptop).
6. **AI tab.** Recommended: parked statement plus the M10 record. Alternative: hide the tab until AI returns (the route already exists, so I advise keeping it honest rather than hiding it).
7. **Data.** Recommended: engine-generated static file with a freshness spec. Alternative: hand-typed tables (can silently go wrong).
8. **Stale registry text.** Recommended: replace the "illustrative mock data" description and keep `/dev/*` stubs unchanged.
9. **Your review of the claims.** Recommended: you read the final wording of the Simulator and Calibration statements before they ship, since they describe how good the model is.
10. **Slicing.** Recommended: two commits. First the generator, data file and freshness spec; second the three tabs and their tests. Pushed only when you say so.

## 7. Test plan

- **Freshness:** the stored data equals a fresh run (within a last-digit tolerance); the Erlang C maths is itself checked against known values; the model's one-server wait equals the exact M/M/1 value.
- **Honesty:** every number on the page comes from the data file; Calibration shows no numbers; the AI tab shows no comparison numbers; the page never uses words like "validated" or "accurate" without the qualification; every command shown is a real script.
- **Pages:** one heading each, correct titles and breadcrumbs, no horizontal overflow at 320, 390, 1024 and 1440 px, no API calls; if public, works for a guest.
- **Deliberate breaks:** a wrong Erlang C term, a changed constant in the engine, a stale data file, a mock number slipped onto Calibration, a missing "not yet measured" status, a command that does not exist.
- The usual gates: type check, lint, all unit tests, full Chrome regression, commit by path, protected audit file never staged.

## 8. Not in scope

A real calibration experiment, any AI evaluation, changing the engine's formulas, the `/dev/*` pages, and an in-app "re-run the evaluation" button.

## 9. Risks

Readers may take "the port matches the prototype" for "the model is accurate"; each item says what it does not show. The Erlang C finding is uncomfortable but real; hiding half of it would defeat the purpose of a proof page.

## Commit one result (2026-11-01): the evidence and its guard
**Built:** `pnpm fixtures:evaluation` (and `:check`) runs the real engine and writes `web/src/lib/evaluation-data.json` (85 KB). `src/modules/simulation/evaluation-data.spec.ts` fails if the stored file differs from a fresh run (within 1e-9), checks the Erlang B and C maths against closed forms worked out by hand, and tests that each consistency check really rejects a violation. Every model value in the table is produced by calling the engine's own `nodeModel`, so it cannot drift from a copy of the formula.
**Final numbers (these replace the preliminary ones above):**
- **One server:** the model equals the exact textbook wait (worst relative error 3e-16).
- **Several servers:** over 16 server counts from 1 to 480 and loads of 5% to 98%: where the exact wait is at least 20% of one service time, the worst relative error is **15.2%** (327 points); at least 5%: **43.2%** (487 points); at least 1%: **115.2%** (635 points). The largest absolute gap anywhere is **0.0336 of one service time** (2 servers, 61% busy).
- **Typical components** (servers per replica from the catalog): the app tier (13 servers, 22 ms) at 70% busy waits 0.95 ms exactly and 1.22 ms in the model; at 90%, 10.6 against 10.8 ms. The external service (27 servers, 180 ms) at 70% busy: 1.2 against 2.2 ms. Near saturation the two agree to within about a percent.
- **Port fidelity:** 4,437 numbers compared against the six reference fixtures (simulation, paths, timeline, breaking point and load curve); largest difference 1.1e-16 (absolute) and 2.3e-16 (relative), against a tolerance of 1e-6.
- **Consistency:** five checks on each of the six templates, all 30 pass: deterministic, idle at zero load with finite times, the load curve never improves with more load, the goal is met just under the breaking point and not at it, doubling replicas never raises utilization.
**Evidence:** backend unit 262 pass (9 new); type check and lint clean for the new files; 16 deliberate breaks to the engine, the Erlang maths, the checks and the stored file; 13 caught first time, 3 survivors explained (the region table is not used by this evaluation; two weakened checks were invisible to a freshness test, so the checks became small exported functions with direct tests, and are now caught). No UI changed, so no browser run for this commit.
