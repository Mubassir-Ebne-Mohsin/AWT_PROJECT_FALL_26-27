## 2. F1: Describe-to-design (revised)

- **Endpoint:** the existing `POST /designs/prepare` gains `source: "ai"` with the same `text` field (1 to 500 characters here, since the model call is paid in quota). The response is the existing prepared design (design plus assumptions), so the existing preview card, validation and Create button are reused unchanged.
- **Model output (strict, all fields required, no nullable unions, because Groq strict mode's handling of unions is unverified):**
  `region` (3 values); `appReplicas` (1 to 50); `includeCdn`, `cdnHitRatio` (0.3 to 0.9); `includeGateway`; `includeLoadBalancer`; `includeCache`, `cacheHitRatio` (0.3 to 0.95); `includeDatabase`; `dbReadReplicas` (0 to 5); `includeQueue`, `queueWorkers` (1 to 20); `includeStorage`; traffic: `rps` (1 to 1,000,000), `readRatio`, `burst` (1 to 20), `sloP95Ms` (10 to 10,000), `errorBudget` (0.001 to 0.1), `durationMin` (1 to 120), `shape` (3 values); `rationale` (at most 200 characters).
  The number paired with an `include…` flag is ignored by the server when the flag is false.
- **Server:** maps the output to `BuilderSpec`, builds with the existing `buildFromSpec`, then validates with the existing `createDesignSchema`; anything outside the ranges is refused, never clamped silently. The rationale may only contain numbers that appear in the user's text or in the returned fields. The assumptions list says "Suggested by a hosted AI model (Groq); review before creating" plus the rationale, marked as model text.
- **Fallback:** none silent. If the model is unavailable the user sees that, and the scripted "keyword rules" path is still offered as its own labelled button, as today.
- **Gate:** 20 prompts as in the plan; the scripted draft is run on the same prompts and judged in the same blind sheet. Pass bar unchanged (18 of 20 sensible and valid, 100% valid or cleanly refused, 0 injection followed, each within 10 s). The report also states AI versus scripted.

## 3. F3: Natural-language what-if (revised)

- **Endpoint:** `POST /ai/tasks/what-if` with `{ designId, expectedRevision, text }` (1 to 300 characters). Returns the interpreted change and its preview result.
- **Model output (strict):** `rpsMultiplier` (0.1 to 20), `shape` (`keep`, `steady`, `ramp`, `spike`), `changeReadRatio`, `readRatio`, `changeDuration`, `durationMin`, `rationale` (at most 120 characters). Traffic only; the graph is never touched.
- **Server:** copies the saved revision's traffic, applies the change, validates with `trafficSchema` (out of range is refused), runs the preview path against the saved graph, and returns the summary together with the saved run's summary.
- **View:** a new side-by-side card, "Same design, different load", titled with both traffic settings, showing p95, error rate, verdict and bottleneck for each, with **no difference column** (the same rule Compare follows). The interpreted change is shown as editable fields; changing them re-runs the preview without another model call. Nothing is saved unless the user chooses **Save these traffic settings as a new revision** (existing PATCH).
- **Gate:** 16 prompts, 14 of 16 correct direction and size, 100% valid or cleanly refused, 0 injection followed.

## 4. F2: Verified fix suggestions (revised)

- **Candidate operations (v1, deterministic, no model):** at the bottleneck node of a saved Fail or Strained run: add one replica; double the replicas (capped at 200); double the capacity; add a cache in front of the database when the bottleneck is the database and no cache exists (using the catalog's default hit ratio, stated as an assumption); add a database read replica when the bottleneck is the database and the read ratio is at least 0.5. At most 6 candidates; each is validated with `graphSchema` and the engine's own validator before it is simulated.
- **Verification:** each candidate is simulated through the preview path at the run's own traffic; only candidates that improve the verdict, p95 or error rate are kept, ranked by verdict, then p95, then error rate; the top 3 are shown. Every number comes from the engine; a test asserts that each displayed number equals a fresh simulation of that candidate.
- **Apply:** one click patches the design (`PATCH` with `expectedRevision`), producing a new revision; the user then runs the test and uses the existing Compare view (same traffic, so it is comparable).
- **AI layer (smaller than planned):** only an intent parser. The user can type a goal; the model returns `priority` (`latency`, `errors`, `fewestChanges`) and one `avoid…` boolean per operation (`avoidReplicas`, `avoidCapacity`, `avoidCache`, `avoidDbReplica`). It only filters and orders the deterministic candidates. **No model-written sentence about a candidate:** the wording of each suggestion is fixed server text, which removes the figure-fabrication risk that failed the explanation gate.
- **Gate:** deterministic core: all 6 templates, Fail and Strained cases, never worse than reported, identical on re-run. Intent parser: 12 goals, 11 of 12 correct.
- **If busy:** previews can be cancelled or refused when the machine is busy; the panel then says "Calculation capacity is busy, try again" and keeps what it had.

## P1 result (2026-11-02): groundwork built, no model called
Nothing here is reachable by a user yet: every task switch is off (`AI_FEATURES` is empty by default) and no endpoint uses the new code. **No request was sent to Groq in P1.**
- **Adapter:** `GroqProvider.structured(task, parse, signal, observe)` for any strict-JSON task. The explanation path and the task path now share one request routine (`complete`), so bounds, redirects, key handling, error mapping, usage reporting and the model check are the same code. The 45 existing adapter tests pass unchanged; 15 new ones cover the task path. Task answers are capped at 1,024 tokens (explanations stay at 2,048), so the quota is not held at the larger figure.
- **Task service (`AiTaskService`):** per-task switch (needs AI enabled and the task listed), hosted model required (the local provider never runs a task and nothing falls back to it), quota reserved before the call and settled to the real tokens after it, a provider rate limit starts the shared back-off, and one row per call in `ai_task_calls` with provider, model, returned model, tokens, latency, outcome, and **only the length and SHA-256 of the person's text**. Failures in the bookkeeping never hide the answer or the real error. `readiness(task)` reports DISABLED, PROVIDER_NOT_CONFIGURED, QUOTA_EXHAUSTED (with the wait) or AVAILABLE and spends nothing. 16 tests.
- **Quota fix found on the way:** the counters are read, changed and written back, which was safe only while one explanation ran at a time. Tasks can arrive together, so `AiQuota` now makes reserve, settle and back-off take turns inside the process (tested: ten simultaneous requests against a limit of three admit exactly three). Known limit: this protects one API process; running several API processes at once would need atomic counters in Redis.
- **Design source `ai`:** contract enum, entity type, regenerated contracts and web types, and the dashboard tag "AI draft". The label is declared when a design is created, exactly as `scripted` is today; it is provenance for the person, not a security boundary.
- **Migration `1794500000000-AiDesignSource`:** replaces the source CHECK (five values) and creates `ai_task_calls` (task limited to describe, whatif, fixes; token and length checks; hash must be 64 hex characters; rows removed with the account). Down refuses to run while any `ai` design exists and never relabels or deletes one. Tested on real PostgreSQL in a throwaway database, up and down (6 e2e tests). **It has not been run on your development database: run `pnpm migration:run` when you want it there.** The e2e suites run it on their own test databases.
- **Settings:** `AI_FEATURES` (comma-separated `describe,whatif,fixes`, default empty, unknown names refused).
- **Evidence:** backend unit 437 pass (2 old skips); e2e 271 pass in 20 suites (6 new); both contract checks identical; backend lint 0 errors, type check clean; web unit 387 pass, web lint and type check clean. Deliberate breaks: 22 tried, **22 caught** (adapter strictness, output cap, size bound, parser use; both switch conditions; quota reserve, settle, back-off and turn-taking; text storage and hash; local-provider guard; bookkeeping and cancel handling; settings; and five on the migration against the real database).
- **A process note:** my first break run was started twice by mistake and the two copies overwrote each other, leaving three of the temporary breaks in the source (the task output cap, the feature switch and the cascade). I found them because later breaks reported "no match", restored them, confirmed the code against the tests, and reran all 22 breaks from a clean state in one process before relying on any result.
- **Not in P1 (moved):** demo mode and the task-generic gate harness, to P2 and P3, as noted at the top.

## P2 result (2026-11-02): describe-to-design built, gate prepared, no live request sent
Everything for F1 is built and tested. **No request has been sent to Groq in P2**, and the task switch is off by default (`AI_FEATURES` empty). The live gate waits for the owner's go. Rubric and procedure: [AI-DESCRIBE-GATE-RUBRIC](AI-DESCRIBE-GATE-RUBRIC.md).
- **Where it lives (a small change from the scope):** `POST /v1/ai/tasks/describe` in the AI module, with `GET /v1/ai/tasks/readiness`, rather than a new source on `/designs/prepare`. The designs module cannot import the AI module without a cycle, and the response has the same shape as a prepared design (plus provider and model), so the existing review card and the existing create path are reused unchanged. The published contract has both endpoints.
- **The form the model fills:** the scope's fields plus a design name (a prepared design needs one), all required, with `include` flags instead of optional parts. The application draws the graph from it with its own builder (`buildFromSpec`, the same one the keyword draft uses) and validates the whole design with its own schemas; out-of-range values are refused, never clamped. The model's one-sentence reason may contain only figures that appear in the person's text (including "200k" and "5 million") or that it chose itself; it is shown marked as the model's own words. The description is sent as a JSON string inside the prompt, never as free text.
- **The page:** on New design, Describe your system. When the server has the task switched on, the page adds the hosted-data notice (what is sent, to whom, up to 30 days kept unless Zero Data Retention, nothing saved until you create), a character counter (500 at most; longer text is refused, never cut), a **Draft with AI** button (off while the quota is used up or the service is not set up, with the reason and the wait) and renames the old button **Draft with keyword rules**. When the task is off the page is exactly the keyword page it was. The review card shows an "AI draft" tag with the model, and creating stores the design with source `ai`, shown as "AI draft" on the dashboard. Leaving the page cancels the model request. Failures are explained in plain words and never replace the workspace.
- **The gate (prepared, not run):** 20 prompts fixed in `describe-cases.ts` (12 ordinary, 3 vague, 2 not about a system, 3 hiding an order), run through the same request and validation as the service, with the keyword draft on the same prompts as the baseline; blind sheet, judgements file and scorer; pass bar 18 of 20 sensible, zero injections followed, each within 10 s. The keyword baseline already fails some mechanical expectations on the ordinary prompts, so the comparison is not against a strawman. `pnpm ai:gate describe-run --dry` and the refusal paths were exercised without a network.
- **Evidence:** backend unit 486 pass (2 old skips); e2e 287 pass in 21 suites (16 new, on real PostgreSQL with a fake hosted model); both contract checks identical; backend lint 0 errors, type check clean; web unit 397 pass (10 new), lint and type check clean. Browser: 9 new tests x 4 projects = 36 pass, including creating an AI-source design on the real migrated backend; full Chrome regression 838 distinct tests passed, 10 skipped by design, 0 failed (the first full run, 28.4 min, had 36 admin and reviewer journeys skip themselves because I had not set their database variables; the files that need them were rerun with the variables set, 56 pass). Deliberate breaks: 26 tried, 25 caught first time, 1 survivor that was dead code (the builder already ignores replicas without a database), removed.
- **Not verified (only a live call can answer):** that Groq accepts this form as a strict schema (booleans, integers, numbers, two enums); how well `gpt-oss-20b` fills it; the token cost per call (the pacer assumes 1,300 and learns from real usage); whether the model respects the ranges or the reason rule.
- **Needs the owner:** run `pnpm migration:run` on the development database (the new design source and task-call table; so far applied only to the disposable audit database); the go for the live gate (20 requests, about 15,000 tokens, a few minutes).
- **Not in P2 (moved):** demo mode needs recorded live responses, so it follows the first live run.
