# R5.2 scope and acceptance plan — learner challenge loop

Date: 2026-10-31. Status: planning approved; this detailed implementation scope awaits review. No R5.2 code started. Sources: R5-INSTRUCTOR-SCOPE.md (eleven approved decisions), existing R5.1 API and challenge screens, route registry, and PROJECT-STATE.md. R5.1 full Chrome gate passed542/552,10 intentional skips; evidence committed015e19a.

## Outcome

Guest browses published challenges → signs in → starts/resumes a private attempt → edits a private design → explicitly submits a saved revision → server evaluates the frozen graph using challenge traffic → learner sees recorded outcome and progress. Works with AI disabled. A submission is the explicit disclosure boundary for future R5.3 Instructor access.

## Included

- Existing /challenges: published-only public list with title, summary and goal. Drafts/archived challenges absent; anonymous responses exclude starting graphs, learner identities and private Instructor account details.
- Existing /challenges/:id: published challenge detail, targets and sign-in/start/resume actions. Do not add routes; registry remains40. Replace unsupported placeholder budget/score promises with actual target/outcome wording; keep navigation and route-audit expectations meaningful.
- Attempt records bind learner, challenge and a private copy of the frozen starting design. Recommended one resumable attempt/design per learner/challenge, with up to20 immutable submissions; independent per-user data and concurrent-start protection. Any later attempt reset/new-copy policy is outside this slice.
- Reuse the existing editor for the copied design. A small attempt context identifies the challenge and offers return/submit. Preserve normal canvas, save, runs, Limits and unsaved-change recovery.
- Explicit submission of a saved revision. The browser supplies identity/revision/idempotency key, never authoritative metrics, verdict, engine version, goal or judging traffic. Unsaved changes require explicit save before submission; do not auto-save or silently discard them.
- Server verifies ownership, binding and revision; snapshots accepted graph inputs and frozen challenge settings atomically; evaluates with existing bounded simulation infrastructure outside a long DB transaction; persists engine version, result and goal comparison. Confirm existing worker/lifecycle conventions before final endpoint/schema design.
- Admission and completion races handled explicitly: stable request key, one logical submission per key, bounded pending work, cancellation/interruption policy consistent with existing jobs, no lost-response duplicate. Count admission toward the20 cap transactionally; state whether failed technical jobs consume a slot and expose a clear recoverable outcome. Recommended technical failures do not consume a graded slot; prevent repeated pending jobs from bypassing admission limits.
- Pass requires p95 <= goal latency AND error fraction <= goal budget. Exact boundaries pass; reject nonfinite/invalid output. Client-edited traffic and pre-existing run IDs cannot influence judging. Clearly distinguish model estimates from measured infrastructure.
- Immutable records include submitted revision/snapshot, challenge identity/settings, timestamps, engine version, outcome and metrics. Later learner edits, challenge wording edits or engine upgrades never rewrite past results. Any recorded pass permanently marks that challenge passed for that learner.
- /progress: authenticated own attempted/passed counts and per-challenge submissions, latest outcome and best result. Recommend best result selection: passed before failed, then lower p95, then lower errors, then deterministic timestamp/id tie-break. Always show actual targets and metrics; no invented score, leaderboard, streak or quiz completion.
- Archived challenges cannot accept new attempts/submissions (recommended); existing attempts, records and permanent pass remain visible through own progress/detail. Return an explicit archived notice and retain edits. This closes archive behavior not specified by the earlier list-only decision.
- Extend dev-only demo seed for four existing catalog names under the demo Instructor, idempotently. Validate each seeded starting graph and record its real baseline; do not claim all starters fail unless demonstrated. Production seed refused; no migration-created demo accounts. Preserve existing instructor identity if demo seed has already run.

## Excluded

R5.3 Instructor submission lists/detail/feedback, reviewer workflow changes, Instructor access before submission, Admin design access, AI hints/judging, automatic graph fixes, grades/cost scores/leaderboards, new routes and production deployment. Existing approved role boundaries remain binding.

## Acceptance tests

Backend/unit/e2e:
- Guests can browse published metadata, cannot start/submit/read progress; draft/archive/private identifiers disclose no private data.
- Two learners cannot access each other's attempt/design/submissions; Admin/Reviewer/other Instructor roles give no bypass. Suspended users denied; no learner email or private notes in public/submission DTOs.
- Starting twice or concurrently resumes one attempt and creates no duplicate design; copying never changes the Instructor's graph. Lost start/submission replies recover with the same request key.
- Submitting changed client traffic, fabricated verdict/metrics, foreign design/run, wrong challenge binding or stale revision fails or is ignored according to strict contract; no accepted fake pass.
- Exact p95/error equality passes, exceeding either fails. Zero error/zero budget cases, strained-without-bottleneck, malformed/disconnected/oversized graphs, worker timeout/restart and unavailable DB covered.
- Concurrent submissions respect20 cap and single accepted key; permanent pass survives later failed submissions/archive/engine change. Archived submission race has a documented linearization point.
- Immutable recorded context survives later edits; version/run retention cannot invalidate a stored submission. Deterministic progress ties and archived progress covered.
- Seed repeat safe, production refusal, four real scenarios with validated baselines. Migration upgrade on isolated data preserves existing users/designs/challenges; rollback tested where practical.

Web/unit/browser:
- Browse signed out → login return-to → start → edit/save → submit → actual result → progress → reload/resume, at1024/1440 light/dark and390mobile smoke.
- Unsaved edit warning, stale save, failed start/save/submit, lost acknowledgement, pending refresh, rapid double-click, account switch/logout and expired session retain correct context without duplicate work or leaked output.
- Public empty list, missing/draft/archive challenge,20 limit, technical judge failure and server outage have readable recoverable states. Keyboard/focus/reduced-motion and overflow checks.
- Mutation checks must catch bypassed ownership, client-traffic judging, stale guard off, wrong AND/OR boundary, duplicate admission, cap bypass and erased permanent pass. Restore each mutation; compile-only failures do not count.
- Backend build/lint/types/unit/e2e, contracts and generated types; frontend build/lint/types/unit and full Chrome regression. Run one heavy job at a time on this laptop, explicit SF_PG_* settings, AI off, isolated data, new evidence paths and pre-run screenshot backup/restore. Preserve protected M2 file exactly.

## Review verdict

The scope forms one demonstrable learner loop and reuses R5.1 plus the tested editor/engine. Main implementation risks: duplicate admissions, tampered judging traffic, async result/context races and accidental access before explicit submission. Resolve these in contracts and server tests before UI. Additional recommended details requiring review are the one-resumable-attempt policy, archive behavior, technical-failure cap policy and best-result tie-break; they are not claimed as previously approved decisions. No completion claim until required checks pass.
